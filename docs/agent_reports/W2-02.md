## 2. OpenWebUI v0.5.10 Integration Architecture Analysis

### 2.1 Frontend Architecture Audit
An inspection of the OpenWebUI v0.5.10 codebase and deployment model reveals that OpenWebUI is built as a single-page application (SPA) using **SvelteKit** and compiled with Vite into static production assets (`/app/build/` containing bundled JavaScript chunks, CSS, and `index.html`).

Unlike desktop IDEs (e.g. VS Code) or micro-frontend host apps (e.g. Grafana), OpenWebUI v0.5.10 **does not expose a dynamic client-side plugin or iframe-tab registration API**. Its extensibility is strictly partitioned into three backend mechanisms:
1. **Tools** (`/api/v1/tools`): Dynamic Python functions exposed to the LLM during generation.
2. **Functions** (`/api/v1/functions`): Python lifecycle filters (`inlet`, `outlet`) and action buttons (`action`).
3. **Static Web Server**: FastAPI serves static frontend assets and REST APIs.

### 2.2 3-Tier Integration Strategy
To deliver a first-class Task Board experience inside OpenWebUI without requiring users to maintain a custom SvelteKit fork or rebuild Docker images, PTB employs a 3-tier architecture:

```
+---------------------------------------------------------------------------------------+
|                               OpenWebUI Application Shell                             |
|                                                                                       |
|   +-----------------------+  +----------------------------------------------------+   |
|   | Left Sidebar Nav      |  | Main Workspace Area                                |   |

|   | [Chats]               |  |  +----------------------------------------------+  |   |

```

1. **Tier 1 — Sidebar Workspace Navigation (Primary UI)**:
   Injected into OpenWebUI's DOM via `scripts/patch_openwebui_board.py`. Adds a native-styled "Task Board" navigation button in the left sidebar that mounts `/board` inside an embedded responsive iframe within OpenWebUI's main content area.

3. **Tier 3 — Direct Dedicated Route (Tertiary UI)**:
   Mounted directly at `/board` and `/workspace/board` by the PTB Application Service / reverse proxy, allowing standalone full-window monitoring on second monitors or mobile devices.

## 3. Implementation Details

### 3.1 Canonical Sort Contract Implementation
In accordance with the frozen Canonical Sort Contract (P1-1 resolution), `ptb_board.html` implements standard sorting across all task listing views:

```
Primary:    status_rank ASC    (IN_PROGRESS=1, TODO/PENDING=2, BLOCKED=3, DONE=4, DISMISSED=5)
Secondary:  priority_score DESC
Tertiary:   due_date ASC       (nulls last)
Quaternary: updated_at DESC
```

#### JavaScript Implementation
- `getStatusRank(task)`: Normalizes status and maps canonical ranks:
  - `IN_PROGRESS` -> `1`
  - `TODO`, `PENDING` -> `2`
  - `BLOCKED` -> `3`
  - `DONE` -> `4`
  - `DISMISSED` -> `5`
  - Unknown -> `99`
- `getTaskPriorityScore(task)`: Extracts `priority_score`, falls back to numeric `priority`, or defaults to `50.0`.
- `parseTimestampSafe(ts)`: Safely parses ISO timestamps or returns `0` for missing/invalid dates.
- `canonicalSortTasks(tasks)`: Implements the exact 4-tier sort logic:
  ```javascript
  function canonicalSortTasks(tasks) {
    if (!Array.isArray(tasks)) return [];
    return [...tasks].sort((a, b) => {
      // 1. Primary: status_rank ASC
      const rankA = getStatusRank(a);
      const rankB = getStatusRank(b);
      if (rankA !== rankB) return rankA - rankB;

      // 2. Secondary: priority_score DESC
      const prioA = getTaskPriorityScore(a);
      const prioB = getTaskPriorityScore(b);
      if (prioB !== prioA) return prioB - prioA;

      // 3. Tertiary: due_date ASC (nulls last)
      const dueA = a && a.due_date ? new Date(a.due_date).getTime() : null;
      const dueB = b && b.due_date ? new Date(b.due_date).getTime() : null;
      if (dueA !== null && dueB === null) return -1;
      if (dueA === null && dueB !== null) return 1;
      if (dueA !== null && dueB !== null && dueA !== dueB) return dueA - dueB;

      // 4. Quaternary: updated_at DESC
      const upA = parseTimestampSafe(a && (a.updated_at || a.created_at));
      const upB = parseTimestampSafe(b && (b.updated_at || b.created_at));
      return upB - upA;
    });
  }
  ```
- **Unified Application**: Applied in `renderTodayList`, `renderTasksComponents`, `renderTasksKanban`, and `renderTasksTable`.

### 3.2 Authentication & API Key Propagation (`X-PTB-API-KEY`)
To address security finding P0-2 and support production environments with API key protection:
1. **Key Discovery & Storage**:
   `getApiKey()` checks the URL query parameter `?api_key=...` first, then falls back to `localStorage.getItem("ptb_api_key")`.
2. **Header Injection**:
   `getApiHeaders(customHeaders)` automatically injects `X-PTB-API-KEY` into every HTTP request:
   ```javascript
   function getApiHeaders(customHeaders = {}) {
     const headers = { 'Content-Type': 'application/json', ...customHeaders };
     const key = getApiKey();
     if (key) {
       headers['X-PTB-API-KEY'] = key;
     }
     return headers;
   }
   ```
3. **Key Configuration Modal (`#apiKeyModal`)**:
   - Header button `#btnApiKeyConfig` opens the configuration modal.
   - Live test connection button (`#btnTestApiKey`) sends `GET /api/tasks?limit=1` with candidate key.
   - Key visibility toggle (`#btnToggleApiKeyVis`).
   - Persistent storage in `localStorage` or instant clear.
4. **Auth Failure Handling**:
   - When API returns `401 Unauthorized` or `403 Forbidden`, the UI immediately updates the status pill to `API Auth Required (401/403)`.
   - Displays an amber warning banner with a direct "Cấu hình API Key" button opening the modal.

## 4. Installer Idempotency & Upgrade Awareness

### 4.1 Version Detection & Compatibility
`integrations/openwebui/installer.py` was enhanced to support version inspection and safe upgrades:
- `get_openwebui_version(openwebui_url)`:
  Queries OpenWebUI's version endpoints (`/api/version` and `/api/v1/version`) to detect the running container version.
- `check_version_compatibility(detected_version)`:
  Validates against `PINNED_OPENWEBUI_VERSION = "v0.5.10"`. Accepts compatible semantic minor/patch releases and flags breaking upgrades.
- `get_install_summary()`:
  Reports server version, compatibility verdict, and whether the operation is a fresh install or upgrade.

### 4.2 Idempotent Execution
- Evaluates `is_upgrade = (dest_dir / "ptb_manifest.json").exists()` before creating/writing files to accurately report operation type.
- Re-running the installer cleanly overwrites integration files (`ptb_board.html`, `ptb_tools.py`, `ptb_filter.py`, `ptb_board_action.py`, `ptb_manifest.json`).
- Uses SQLite `ON CONFLICT(id) DO UPDATE` for OpenWebUI database tables (`tool`, `function`), ensuring zero schema corruption or duplicate keys upon repeated installation.
