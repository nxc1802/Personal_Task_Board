## Executive Summary

Task **W2-07** delivers the authoritative **PTB-Bench-500** evaluation dataset, complete with oracle ground truth annotations, cryptographic SHA-256 manifest locking, deterministic generation tools, and split isolation to prevent data contamination.

### Context & Objective
During the Wave 0 audit (**W0-02**), the historical claim of "100% Accuracy on PTB-HYBRID-500" was found to be invalid: no 500-sample dataset existed in the repository checkout, benchmark tests were bypassed with `FakeDeterministicLLMExtractor`, and real production accuracy on the `SB-v0.1` benchmark measured only **36.8% (14/38)** due to hardcoded `due_date=None`, confidence heuristic failures, and requester attribution loss. In Wave 1, **W1-04** constructed the independent benchmark framework (`benchmarks/`) with a 10-dimension metric scorecard and a mini smoke dataset (12 samples).

**W2-07** provides the full-scale, production-representative benchmark suite:
- **500 total evaluation cases**: exactly **475 raw multi-source event samples** + **25 failure and recovery probes**.
- **Balanced representation across 6 enterprise channels**: Microsoft Teams (85), Microsoft Outlook (85), Slack (80), Jira (80), GitHub (75), and Confluence (70).
- **Comprehensive challenge taxonomy**: 11 categories covering real-world complexities including noise chatter, explicit negation, Vietnamese/English code-switching, near-duplicates, cross-source entity linking, document attachments, ambiguous commitments, and varied date/time expressions.
- **Strict Oracle Ground Truth**: each sample contains precise expected task classification, canonical persona attribution (owner and requester), exact ISO 8601 UTC deadlines, state machine status, and verbatim evidence snippet citations.
- **Data Contamination Safeguards**: stratified splits partitioning into **Dev (235 items / 49.5%)**, **Calibration (95 items / 20.0%)**, and **Locked Final Test (145 items / 30.5%)**. The test split is explicitly locked and forbidden from model training or prompt tuning.
- **Zero PII & Secret Leaks**: all emails restricted to whitelisted corporate domains (`@company.com`, `@partner.com`, `@fpt.com`); zero unredacted API keys, JWT tokens, or credentials.
- **Deterministic Generation & Verification Tools**: `benchmarks/tools/dataset_generator.py` and `benchmarks/tools/validate_manifest.py` ensuring byte-for-byte reproducibility across runs.

## 3. Data Contamination Protection & Split Policy

To ensure sound ML/LLM benchmarking methodology, the dataset is split into 3 mutually disjoint partitions:

```
475 Samples Partitioning:
├── Dev Split         : 235 samples (49.5%) -> benchmarks/dataset/ptb_500/dev_samples.json
├── Calibration Split :  95 samples (20.0%) -> benchmarks/dataset/ptb_500/calibration_samples.json
└── Locked Test Split : 145 samples (30.5%) -> benchmarks/dataset/ptb_500/test_samples.json
```

### Stratification Guarantee
Each split preserves proportional representation of all 6 sources and all 11 challenge categories. Each sample's `origin_reference` explicitly records its provenance:
- Dev sample: `ptb_500://dev/ms_teams/ptb500-001-teams-direct_task`
- Calibration sample: `ptb_500://calibration/slack/ptb500-019-slack-multilingual`
- Test sample: `ptb_500://test/jira/ptb500-045-jira-issue_tracking`

### Strict Anti-Contamination Invariant
The **Locked Test Split (`test_samples.json`)** is frozen and must **NEVER** be used for prompt tuning, fine-tuning, or few-shot example selection. Downstream agents developing extraction prompts or training models must only train and tune on the Dev split, calibrate thresholds on the Calibration split, and run locked evaluation on the Test split once implementation is complete.

## 8. Security & Compatibility Impact

1. **PII and Secret Redaction**:
   - Zero real API keys, bearer tokens, or JWTs exist in the dataset.
   - All email addresses strictly match whitelisted corporate test domains (`@company.com`, `@partner.com`, `@fpt.com`).
2. **Cryptographic Tamper-Proofing**:
   - Manifest validation unconditionally verifies SHA-256 hashes of all dataset files on disk.
   - Any accidental modification or character corruption immediately triggers a hard error before pipeline evaluation runs.
3. **Cross-Platform Hash Stability**:
   - Hashing normalizes `\r\n` line endings to `\n`, ensuring that git checkouts on Windows and Linux produce identical SHA-256 checksums.
4. **Zero Production Runtime Impact**:
   - Dataset files and generator tools reside exclusively in `benchmarks/` and do not alter application or server behavior.
