## 1. Frozen Canonical Sort Contract

The canonical sort contract is frozen across all layers (Neo4j Cypher queries, Repository domain logic, Application API, and Intelligence Daily Planner):

| Priority | Dimension | Order | Null / Tie Handling | Logic / Value |
| :--- | :--- | :--- | :--- | :--- |
| **Primary** | `status_rank` | **ASC** | Fallback rank 6 | `IN_PROGRESS=1, TODO=2, PENDING=2, BLOCKED=3, DONE=4, DISMISSED=5` |
| **Secondary** | `priority_score` | **DESC** | Default 0.0 | Respects `priority_override` if present, else `priority.total_score` or `priority_score` |
| **Tertiary** | `due_date` | **ASC** | **Nulls Last** | Smaller timestamp first; `None` mapped to far-future `9999999999.0` (year 2286) |
| **Quaternary** | `updated_at` | **DESC** | **Nulls Last** | Larger timestamp first; `None` mapped to far-past `-62135596800.0` (year 0001) |

### Mathematical Equivalence Across Ascending and Descending Sorts

In `TaskDomainRepository.list_tasks` (standard ascending sort, `reverse=False`):
$$\text{SortKey}_{\text{repo}}(t) = (\text{rank},\ -\text{score},\ \text{due\_ts},\ -\text{updated\_ts})$$

In `TodayBoardPlanner.plan_today` (descending sort, `reverse=True`):
$$\text{SortKey}_{\text{planner}}(t) = (-\text{rank},\ \text{score},\ -\text{due\_ts},\ \text{updated\_ts})$$

Because every component of $\text{SortKey}_{\text{planner}}$ is exactly $-1 \times \text{SortKey}_{\text{repo}}$, the resulting sort order for any arbitrary sequence of tasks is **mathematically identical**.

## 2. Root Cause Analysis & Code Remediation

### 2.1 P1-1: Sort Order Drift in `planner.py`
- **Location:** `services/intelligence/src/ptb_intelligence/planner.py:155-161`
- **Root Cause:**
  ```python
  # Old code in planner.py:
  def _today_sort_key(item: TodayTaskItem):
      st = str(item.status.value if hasattr(item.status, "value") else item.status).strip().upper()
      is_in_progress = 1 if st == "IN_PROGRESS" else 0
      score = float(item.priority.total_score if item.priority else 0.0)
      return (is_in_progress, score)

  today_task_items.sort(key=_today_sort_key, reverse=True)
  ```
  `is_in_progress` only discriminated between `IN_PROGRESS` (1) and all other statuses (0). As a result, `TODO` and `BLOCKED` were given equal status weight (0), allowing a high-priority `BLOCKED` task (e.g. score 95.0) to jump ahead of a medium-priority `TODO` task (e.g. score 40.0).
- **Remediation:**
  Replaced with canonical 4-tuple `_today_sort_key(item, tasks_map)`:
  - Evaluates `STATUS_RANK = {'IN_PROGRESS': 1, 'TODO': 2, 'PENDING': 2, 'BLOCKED': 3, 'DONE': 4, 'DISMISSED': 5}`.
  - Resolves `score` from `item.priority.total_score`, `priority_override`, or `priority_score`.
  - Normalizes `due_date` using `_safe_timestamp(due_val, default_ts=9999999999.0)`.
  - Resolves `updated_at` from `item` or `tasks_map[item.task_id]` and normalizes via `_safe_timestamp(upd_val, default_ts=-62135596800.0)`.
  - Exposed `TodayBoardPlanner._today_sort_key = staticmethod(_today_sort_key)` for direct testing.

### 2.2 Date/Time Type Robustness in `task_repo.py`
- **Location:** `packages/database/src/ptb_database/repositories/task_repo.py`
- **Root Cause:**
  `_task_sort_key` called `.timestamp()` directly on `t.due_date` and `t.updated_at`. If either attribute was a string (e.g. ISO formatted string from raw payloads or external JSON) or a naive datetime, Python would raise `AttributeError` or produce mismatched timezone offsets.
- **Remediation:**
  Introduced `_safe_timestamp(val, default_ts)` helper that reliably converts aware datetimes, naive datetimes (assumed UTC), `datetime.date` objects, numeric timestamps, and ISO 8601 strings into normalized UTC float timestamps. Defined `_task_sort_key` at module level and exposed as `TaskDomainRepository._task_sort_key = staticmethod(_task_sort_key)`.
